# Provenance And Data Format Support Notes

The experiment core model must make ACES data exportable, linkable, and
auditable. These notes focus on published academic sources that justify support
for structured metadata, provenance, and research-object packaging.

## Experiment Metadata Precedents

OpenML and experiment databases are the closest ML precedent for EXP-701
through EXP-705:

- Vanschoren et al. 2014, OpenML. DOI: 10.1145/2641190.2641198.
- Vanschoren et al. 2012, experiment databases. DOI:
  10.1007/s10994-011-5277-0.

Important modeling lessons:

- Dataset/scenario-like artifacts are not tasks.
- Tasks define an evaluation problem over data/scenario artifacts.
- Runs bind an executable flow/process to a task.
- Evaluations attach result values to runs and tasks.
- Collections/benchmarks support comparison and meta-analysis.

ACES translation:

- `scenario` or `scenario_snapshot` is the authored/runnable cyber-range
  environment.
- `experiment_task` is the evaluation problem over that scenario.
- `processor` and `backend` are part of execution apparatus, not task meaning.
- `experiment_run` is the archival execution activity.
- `run_result` and `evaluation_result` artifacts hold measured outcomes.
- `study` and `collection` organize tasks/runs/results for comparison.

## Ontologies And Vocabularies

Published ML and scientific-experiment vocabularies reinforce the need for
separable entities and relations:

- MEX vocabulary. DOI: 10.1145/2814864.2814883.
- OntoDM. DOI: 10.1007/s10618-014-0363-0.
- Ontology of scientific experiments. DOI: 10.1098/rsif.2006.0134.

Design consequences:

- Avoid one polymorphic `experiment` object that tries to mean task, run, and
  study at once.
- Use explicit relationship names: task uses scenario; run executes task; run
  uses apparatus; result was generated by run; study includes tasks/runs/results.
- Reserve controlled vocabularies for roles, result kinds, apparatus component
  kinds, protocol stages, and run outcome states.
- Add extension points that can later map to semantic vocabularies without
  changing ACES-owned authority.

## Provenance Model Requirements

PROV and the Open Provenance Model show why provenance should be graph-like:

- Moreau et al. 2011, OPM. DOI: 10.1016/j.future.2010.07.005.
- Moreau et al. 2015, PROV rationale. DOI: 10.1016/j.websem.2015.04.001.

ACES does not need to adopt every PROV artifact as the internal schema, but the
model should be mappable to provenance concepts:

- scenario snapshots, task specs, manifests, logs, metrics, and result files are
  entities;
- run execution is an activity;
- processor, backend, operator, participant role, and automation may be agents;
- derivation links connect results to run evidence and run evidence to
  apparatus inputs;
- invalidation or supersession should be explicit when a run is retracted or a
  task version is replaced.

Design consequences:

- Every task, run, study, metric definition, apparatus declaration, and result
  artifact needs a stable identifier and version/snapshot policy.
- Run records need `used` references for scenario snapshot, task version,
  manifests, backend profile, processor manifest, parameter set, and stochastic
  controls.
- Result records need `was_generated_by`-style links to runs, plus evidence
  artifact references.
- The design should distinguish archival run records from live control-plane
  lifecycle events because provenance requires durable historical facts.

## FAIR And Research Object Packaging

FAIR and RO-Crate literature supports machine-readable packaging and reuse:

- Wilkinson et al. 2016, FAIR Guiding Principles. DOI:
  10.1038/sdata.2016.18.
- Soiland-Reyes et al. 2022, RO-Crate. DOI: 10.3233/DS-210053.
- Balenson et al. 2022, FAIR cybersecurity artifacts. DOI:
  10.1145/3546096.3546104.

ACES implications:

- Records need globally stable or at least repository-stable identifiers.
- Artifact metadata should include type, role, media type, checksum, size,
  creation time, source, and access constraints.
- Collections should be exportable as a bundle with metadata and related
  artifacts, not only as loose database rows.
- The design should support JSON/JSON-LD-like package mapping for future
  RO-Crate export without making JSON-LD the only internal representation.
- Sensitive cyber-range evidence may require access-control and redaction
  metadata while still preserving findability and provenance inside the
  authorized archive.

## Workflow And Computational Context Capture

Computational reproducibility tools emphasize automated capture of environment
and workflow context:

- CWLProv. DOI: 10.1093/gigascience/giz095.
- Sumatra. DOI: 10.1109/MCSE.2012.41.
- ReproZip. DOI: 10.1145/2882903.2899401.
- noWorkflow. DOI: 10.1007/978-3-319-16462-5_6.
- Popper convention. DOI: 10.1109/IPDPSW.2017.157.
- MLflow developments. DOI: 10.1145/3399579.3399867.

ACES implications:

- Apparatus context should contain processor identity, backend identity,
  selected manifests, compatibility declarations, configuration, parameters,
  stochastic controls, and setup context.
- Apparatus should be captured as structured context, not just human notes.
- Raw backend logs and manifests can be evidence artifacts, but the ACES
  normative schema should define the canonical summary and references.
- The system should be able to record both planned setup and observed setup.
  Mismatches are important evidence for reproducibility and drift analysis.

## Data Format Support Criteria

The design should support the following export and schema needs:

- ACES-owned JSON-compatible contract schemas for task, run, apparatus, study,
  collection, metric definition, result summary, and artifact references.
- JSON Schema publication in the repo's existing contract publication mechanism.
- Provenance mapping to PROV-like entity/activity/agent relations.
- RO-Crate-like packaging where a study or run archive can carry task specs,
  scenario snapshots, apparatus context, result summaries, raw evidence, and
  analysis artifacts.
- OpenML-inspired indexing and comparison: tasks, runs, and evaluations must be
  queryable without reading every raw artifact.
- Controlled vocabularies for lifecycle status, result kind, artifact role,
  apparatus component kind, stochastic-control kind, protocol-stage kind, and
  validity-threat category.
- Extension fields with declared namespaces and schema policy so cyber-range
  backends can preserve specialized evidence without taking over ACES schema
  authority.

## Anti-Patterns To Avoid

- A single `metadata` dictionary as the only place for apparatus context.
- Treating run status events as the final archival run record.
- Storing only display names for processors, backends, tasks, or scenarios.
- Recording metrics as name/value pairs without metric definition and unit.
- Baking raw OpenML, MLflow, RO-Crate, or PROV payloads into ACES core schemas.
- Allowing result records to exist without task, run, and apparatus links.
- Allowing studies to be arbitrary folders of files with no analysis intent.
